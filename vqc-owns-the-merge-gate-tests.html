Making vqc/ the home of the merge gate's tests

This page prepares the design session on Tom's todo of October 14, 2026: VQC should own the tests the merge gate runs, so that every test is in the place where he specifies what quality code means, and all Jarvis code is held to that standard. It explains what VQC is today and what the gate runs today. It then proposes what it would mean for a vqc/ directory to own the gate's tests in Jarvis, tom.quest and WikiTom, asks for three rulings, and reports the two Codex audits of earlier versions (section 6). The facts were read from the session branches of the four repositories on October 14 between 9:07 and 9:50 pm Eastern; nothing has been built.

The drawing above is the proposed end state. A builder, the session that edits a repository, pushes a branch to the box's bare repository. The gate, the program on the box that lands branches on main, reads the pushed head and runs the same commands it runs today. What changes is where the files those commands run sit. Every test file and every check script moves from beside the code into the repository's vqc/ directory, which becomes their home. Each runner is pointed there, and one new check turns red if a test file sits anywhere else. The walls, the audit, the step table, the rows the gate writes and the way main moves stay as they are.

1. What VQC is today, in ComplexMultiTrigger

VQC stands for Verified Quality Code. It is Tom's code-quality governance, first built in his research repository ComplexMultiTrigger (CMT). Its purpose, as he put it on September 1, is that he can trust an agent when it says a change is high quality. On September 24 he drew its boundary: VQC holds formal rules that are enforced in code, and the reasons he cares about them live in Jarvis's model of him, not in VQC.

The law is vqc/constitution.md, version 4. It describes itself as codebase-independent and says it governs form, not content. It is ranked from the most fixed to the most local. Three axioms state premises about agents. Nine ideals, numbered C1 to C9, state goals; for example, C1 says every piece of knowledge has one home, and C3 says fail loudly. Thirty-one doctrines, numbered D1 to D31, are strategies that carry out the ideals. Statutes are the per-repository data that bind the law to one tree. The axiom that matters most for this design is A3: "Executable law binds deterministically; prose influences probabilistically." So a rule that must always hold must be a check that runs.

Four of the constitution's ideas bear on this design. Each is VQC's own term, defined in the constitution:

VQC termWhat it means
ClaimA statement about the code that must stay true. Doctrine D7, claims-not-tests, says claims are what must stay covered, and that claims are derived from the checks (from their witness faults and from the registries they read), not declared in prose. It rejects counting tests as a measure. A test may be deleted when every claim it covered is still covered.
Witness faultA small, written-down defect that a check exists to catch. Doctrine D8 says every new check is born with at least one. A harness proves three things: the suite is green without the defect, this check turns red with it, and a sample of other checks stays green with it, so a defect that breaks everything proves nothing.
Ledger entryA dated entry in vqc/ledger.yaml for something known to be not yet true, with the condition that closes it. CMT's ledger holds 356 entries (counted by grep -c '^- id:').
Ratchet-adoptionA new check lands as a gate for new cases, and every existing violation is written into the ledger as dated debt, never exempted silently.

The fact that shapes this design is that CMT's vqc/ holds the law and its data but no tests. The checks that enforce the law are pytest files outside it. tests/guards/ holds 28 test files, which check the ledger's shape, that generated text matches its source, and that every binding article is either carried out or recorded as debt. tests/faults/ holds the witness faults and their runner. CMT has no gate. It has no CI and no hook of its own (the box's checkout uses Jarvis's hooks), and a merge is Tom's own step after an agent has run pytest.

2. What VQC is today, in tom.quest

tom.quest adopted VQC on August 27, by Tom's ruling to apply the constitution and ignore CMT-specific articles. Its vqc/adoption.md switches off five doctrines (D15, D16, D17, D22 and D30) and cites the constitution in CMT without copying it.

tom.quest's vqc/verifiers.md sets a constraint this design must keep. It says there are exactly three verifiers, the sources of the rows the merge gate reads:

VerifierWhat it isWhat it writes
ChecksEvery deterministic check: a program answering by string, count, schema or regex.The tests-run row for the head
The auditA model of another family reading a change before it merges.The audit-verdict row for the head
The evalsA model reading outputs against Tom's labels.One eval-run event per set

Two of the three write a row the merge gate reads; the evals write events the gate does not read. Its rule is: "a new deterministic check is a test, a new judgment of a change is part of the audit's prompt, and a new judgment of an output is a case in the evals. There is no fourth row, and there is no register of verifiers — a register would be a cross-cutting dimension every future change had to satisfy, which is the wicked feature Tom's 2026-09-11 ruling refuses." A list that every new test had to be entered in would be such a register. That was the first version of this page, and the audit rejected it (section 6). Putting the test files themselves in vqc/ needs no list.

Its own tests are two vitest files inside vqc/ (9 tests). They check the shape of its ledger (20 entries), its todos (16), its steering entries (5) and its rulings log (15 rulings). tom.quest also keeps a prose inventory of every test and check in docs/tests.md.

Jarvis and WikiTom have no vqc/ directory. VQC is mentioned in WikiTom's explainers and sources, but no directory there holds VQC files.

3. What the gate runs today, and where a quality claim reaches Tom

The gate (Jarvis worker/jobs/gate.mjs) runs every minute. For each pushed head it works in a fixed order. It checks that the head contains main. It runs the walls, the checks that refuse a secret's value or a key's shape and, in a public repository, a model-of-tom line or a private path. It runs the repository's checks, unless a tests-run row for that exact commit is already on record (rows are written once per commit and kept). It runs the audit when the change touches a wall, a git hook, setup.sh, worker/cron or one of the gate's own files, or when a commit carries the trailer Complex: yes. It then asks the record whether the gate is open and, if so, moves main. The record's answer (GET /tts/merge-gate) is yes when the head's tests-run row says passed and its audit-verdict row says APPROVED. There is one exception: the nightly job pushes WikiTom's snapshot and vocabulary commits straight to main, "by design: its snapshot and vocabulary commits are no change anybody reviews" (convex/ttsMerge.ts), and a nightly-run row opens the gate for them. The nightly recheck runs WikiTom's checks after that push.

No list says which tests run. A table written into pull-request-checks.mjs gives each repository a mode, and the mode fixes an install step and a sequence of steps. Jarvis's and tom.quest's steps run in a memory-capped systemd scope with a 10-minute limit; WikiTom's run with a timeout and no memory cap. The nightly recheck (worker/jobs/recheck.mjs) runs each repository's checks again on main and writes a job-ok or job-failed event, not a tests-run row. For Jarvis and WikiTom it reads the same table; for tom.quest it reads the GitHub workflow's steps.

So today the definition of what a repository's checks are lives in two places. Jarvis's code fixes the steps. Each repository's package.json and runner configuration fix which files each step collects, and they are read from the head being judged. Nothing in any vqc/ takes part. Runners also skip some tests they collect: tom.quest has one unconditional skip (e2e/perfume.spec.ts:30) and several that need credentials or real data, and Jarvis has skips by platform. A runner can also miss a file entirely. Jarvis's vitest collects only worker/, scripts/ and test/, and tom.quest's nine Python test files are collected by nothing.

A quality claim reaches Tom in fewer places than one might assume. The tests-run and audit-verdict rows are read by the gate, and the audit reads the tests-run row. A grep for both names in tom.quest/app found no page that shows them. The gate sends its verdict (landed, blocked or rejected) as a message to the session that pushed. Before pushing, the builder runs two things on its commit. Its pre-review, a subagent reading the diff, writes no row. jarvis audit on the exact commit posts the audit-verdict row the gate then reads. The sessions page shows only "deployed" and a commit hash.

4. What it means for vqc/ to own the gate's tests

In this version, vqc/ is the literal home of every test: each test file and each check script in Jarvis, tom.quest and WikiTom sits under that repository's vqc/. Nothing else about the gate changes. The gate runs the same commands, so the rows it writes certify the same thing they certified the day before the move. This design came out of two rejected versions. Both moved the definition of what runs into vqc/ while the files stayed beside the code. The audits found that a list of tests is the register verifiers.md refuses, and that the commands the gate runs are bound up with the gate's own orchestration and cannot be lifted out of Jarvis. Moving the files and leaving the commands untouched has neither problem. The state the work leaves behind is this.

What a vqc/ directory contains

PathWhat it holds
vqc/adoption.mdWhich articles of the constitution apply to this repository, where its statutes live, and its rulings log, as tom.quest's does today. Jarvis and WikiTom write theirs for the first time.
vqc/ledger.yamlDated known gaps, each with the condition that closes it.
vqc/tests/Every test file, at the same relative path as the code it tests. For example, Jarvis's worker/jobs/gate.test.mjs becomes vqc/tests/worker/jobs/gate.test.mjs. Fixtures move with their tests.
vqc/checks/Every check script that is not a test: Jarvis's seven scripts/check-*.mjs, tom.quest's eight guardrail scripts, and WikiTom's evidence check.
vqc/e2e/ (tom.quest)The Playwright specs.
vqc/tests.md (tom.quest)Today's docs/tests.md, moved, with its stale per-directory counts removed. It is an overview, not an authority on which tests exist; the directory itself is.

The directory names under vqc/ are proposals, and Tom may rename them. tom.quest's existing vqc/ files (verifiers, ledger, todos, steering, classification and their two tests) stay where they are. Its two tests move into vqc/tests/vqc/.

How a test gets in

An agent writes the test under vqc/tests/. Each runner's configuration collects only from vqc/: vitest's include patterns, Playwright's testDir, and the node --test pattern Jarvis's code runs for WikiTom. So a test written there runs at the next push, with no entry to make anywhere.

What happens to a test written anywhere else

A runner that collects only from vqc/ would never collect it, and nothing would say so. That has already happened twice. tom.quest's nine Python tests in turing-api/ are collected by nothing, and Jarvis's vitest today collects only worker/, scripts/ and test/. So one new check, the location check, runs in each repository's existing check step. It turns the tests-run row red when any file named like a test (*.test.*, *.spec.*, test_*.py, *_test.py) exists outside vqc/. The silently-uncollected test cannot be deleted instead, because it is created by any agent that writes a test in the usual place next to its code. The check is born with its witness fault, VQC's D8. Its own test plants a test file outside vqc/ in a temporary tree and expects red, expects green without it, and expects the repository's other checks to stay green under it. tom.quest's nine Python tests move to vqc/tests/turing-api/. They are still collected by nothing, which is a dated ledger entry that closes when a step runs them. Deleting them needs evidence that what they cover stays covered (D7).

How the gate reads it

It does not change. The gate, the pull-request checker and the recheck run the same commands (pnpm run verify, tom.quest's six steps, the GitHub workflow's jobs, WikiTom's two commands). Those commands now collect from vqc/. Two things in Jarvis's code change for WikiTom only. The node --test pattern collects from both scripts/ and vqc/ for the duration of the move, then from vqc/ alone. The three WikiTom checkouts (the gate's, the pull-request checker's and the recheck's) add vqc/ to the paths they hold. tom.quest's affected-tests selection follows imports, not directories, so it keeps working after the move.

The order of the move

  1. Jarvis first, end to end. One branch moves every Jarvis test and check under vqc/, rewrites their import paths, points vitest's include and package.json's check scripts at the new paths, and adds the location check. It lands through the gate green. A second branch that places a test outside vqc/ is blocked. This is the first path the agent rules require: proven by working, not by tests passing. Undoing it is reverting that one landed commit.
  2. Jarvis's code learns WikiTom's new paths: the dual node --test pattern and the three checkouts.
  3. tom.quest and WikiTom move in parallel, each in one branch, under the same rules. Each repository's move is one landed commit, reverted alone. Jarvis's dual pattern is narrowed to vqc/ after WikiTom's move lands.
  4. Jarvis and WikiTom write their adoption clauses. Every article of the constitution that applies but is not met is written as dated ledger debt (VQC's ratchet-adoption), including the missing witness faults for existing checks and the conditional skips. An agent reads the constitution article by article against the repository to produce this; nothing gates on it.

5. Rulings requested

  1. Whether the test files move. If they move, vqc/ is the home of every test, as the todo says. One directory holds every test and every check, and the gate is untouched. The cost is one large mechanical move per repository: about 296 test files and the check scripts, their import paths and runner patterns. After it, a test no longer sits next to the code it tests, though it sits at the mirrored path under vqc/tests/. If they do not move, vqc/ keeps only the law, ledger and adoption clauses in each repository, and the todo's "home for all tests" is not met. Both earlier ways of meeting it without moving the files were rejected by the audit. Recommendation: move them, because it is what the todo says, and because it is the only version of this design that leaves the gate's commands untouched.
  2. Whether the location is enforced by a check or by a rule line. With the location check, a test written outside vqc/ turns the row red, at the cost of one more check (with its witness fault) in each repository's check step. With a line in each AGENTS.md instead, the runner silently skips a misplaced test, which VQC's axiom A3 says a prose rule cannot prevent ("prose influences probabilistically"). Recommendation: the check, for the two occurrences named in section 4.
  3. Whether the audit's criteria move into vqc/ too. The gate reads two verifiers, the tests and the audit. The audit's questions are in Jarvis's audit.mjs: would landing this break something or do something nobody asked for, weakened or removed tests, secrets, boundaries, deletions of things still used. That file is one of the gate's own, so changing them needs an audit. If only the questions move to vqc/audit.md in Jarvis, vqc/ states everything that opens the gate. Under agent-rules.md:33 that file is a rules file and needs no audit to change. It is read from Jarvis's main, so a change is judged under the questions already landed and never its own. The output format and verdict protocol stay in audit.mjs. A missing or unreadable criteria file makes the audit answer UNAVAILABLE, which keeps the gate shut, and the audit row records which commit of the criteria it used. If the questions stay, they keep the audit's protection, but vqc/ states only the tests half. Recommendation: move them, because the todo calls VQC how Tom specifies what quality code means, and the audit is the other half of that at the gate.

Two decisions are taken, not asked, and Tom may object to either. First, the law stays in CMT. Jarvis's and WikiTom's adoption clauses cite it as tom.quest's does, because nothing in this design reads it and CMT's guards depend on its current path. Second, I read "all Jarvis code" as the three repositories the gate lands, Jarvis, tom.quest and WikiTom, and not CMT. This reading is inferred.

6. The Codex audits of earlier versions

By Tom's ruling of October 14 ("the design sessions should run codex audits over their design when they are done"), each version was audited by one read-only Codex process (gpt-5.6-sol). Each audit was given his words and the rules the design rests on, quoted with file and line, and asked for every deviation and every case not covered. The agent rules (agent-rules.md, under Committing and merging) stop a design after its third rejection.

The findings of the two rounds, read together, give the reason for version 3. Version 1's central defect was that a list of every test is the register verifiers.md refuses: "a cross-cutting dimension every future change had to satisfy". It also declared claims that D7 says are derived, not declared. Version 2's blocking findings had one cause. Its steps file could not express what tom.quest's checks need, which is the base and head commits, the affected-or-full mode and the summary file the row is built from. The install, memory scopes, kill-and-retry handling and recheck behavior were all left without a home. And the switch could not be undone repository by repository. All of these follow from moving the execution contract out of the gate, which is where it belongs. Both audits also said the recommendation against moving the files departed from the todo's words. Version 3 keeps the gate's execution where it is and moves only the files, which resolves both causes. These version 2 findings no longer apply to version 3, because they concern the steps file it drops: the schema, the install policy, kill-and-retry, recheck's own behavior, rows certifying different commands, and fail-loud validation of a steps file. The factual errors both audits found are corrected in sections 1 to 3.

The third audit is held until Tom has ruled. A third rejection stops iteration on a design, and the choice it would judge, whether the files move, is Tom's to make. The audit then runs on the design as he rules it, before any item is filed.

9. What this leaves unchanged

The gate, its step table, the commands each repository runs, the memory scopes and limits, the walls, the audit's triggers and models, the evals, the two rows the record reads, and how main moves all stay as they are. The code under test does not change; only the tests' and checks' paths and import lines do. CMT is not touched.

10. What happens next

When Tom joins, we work through the three rulings. The design as he rules it then goes to the third Codex audit. After his explicit go and an approving audit, the session writes the items to build to /var/lib/tts/design-vqc-work.txt for his desktop session: for each item, the files it touches and the items it waits on. If the third audit rejects, the design goes back to Tom with every finding of the three rounds, not to a fourth version.
