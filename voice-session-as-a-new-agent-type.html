A voice session: an agent Tom talks to out loud

This page proposes a new kind of agent for Jarvis and explains it from the ground up for a reader who has seen none of it before. Jarvis is Tom's agent system: a set of programs and model-driven agents running on one rented Linux machine, called the box, which keeps his food and exercise records, his todo list, and builds the software he asks for. A session is an agent Tom talks with. Today every session is typed: he writes to it and it writes back. The proposal here is a session he speaks to and which speaks back, continuously, while he is doing something else — first inside a wearable prop, and after that anywhere he is.

Every claim about the speech model's behaviour was read from OpenAI's published documentation on 12 October 2026, and where that documentation is silent the sentence says so, because several of the gaps change what should be built. Every claim about Jarvis was read from the agent rules and the Jarvis repository the same day. Where a conclusion is mine rather than documented, it is marked.

Legend

One shape per type of thing, one line style per type of relation, the same on every drawing. A page is something you look at on tom.quest. A program is a process on the box that runs no model. An agent is a process that runs a model: a session, a subagent, a worker, the delegate. A store is data at rest: a database, a directory, a checkout. A wall is a check that can refuse an action without trusting the agent. A record row or document is a structured thing passed between parts: a work order, a brief, a row in the record. A state is one stage in a lifecycle. A solid arrow carries data or a message; a dashed arrow means the source starts the target; a dotted arrow means the source reads the target; the barred red arrow means the source can refuse what the target is doing. A dashed frame groups the parts inside it. On a drawing of a design, a plain outline is kept; an amber dashed outline is replaced, and its second line names what replaces it; a grey dashed outline with a strike is removed; a blue dashed outline is proposed, a part that does not exist yet.

The whole proposal at a glance

Four things already exist and are drawn plain: Tom, the box, the record, and the website tom.quest. The record is the database behind that website, holding his food and exercise facts, his todos, and a row for every change Jarvis makes to its own code. Everything drawn with a blue dashed outline is new.

Tom speaks. A page open in the browser on his phone carries his voice to OpenAI's speech model and plays the reply. That page holds no credential and knows nothing about him. Separately and at the same time, a new program on the box attaches to the very same conversation over a second connection, watches the running transcript of both speakers, and feeds text into the conversation when it has something to contribute. When a question needs real work, that program starts an ordinary Jarvis agent — a model with the box's full set of tools — and hands back what it finds.

The division is the whole idea, and the next section explains why it is forced rather than chosen. The phone is a mouth and an ear. The box is the mind. They meet inside one conversation held on OpenAI's side.

What a session is today, and what a voice session changes

A session today is a conversation Tom has by typing into a page on tom.quest. It has exactly two durable parts: a row in the record naming it, and a transcript file in a directory on the box that both of the box's two logins share. A reply is one operating-system process running the Claude Code command-line tool: it starts when a message arrives, writes its answer, and exits. Between replies nothing is running. Five sessions never end and have fixed jobs — one takes his dictated facts, one writes his morning briefing, one builds code, one files corrections and failures, one keeps the todo list — and each is defined by a short text file in the Jarvis repository. A program on the box called the session host does the mechanical part: it takes each message the website received, runs one process under the right login, and writes the result back.

A voice session keeps the two durable parts and changes everything about the middle. There is no process that starts and exits per reply, because the conversation is continuous: audio flows both ways without pause and the model itself decides when to talk. There is no message to dispatch, so the existing session host has nothing to do and is not involved. The model is not Claude but a different speech model from a different supplier, which cannot run the box's tools itself. And the conversation happens aloud, in a room, where other people can hear it and speak into it — which is the first time any agent in this system has been addressable by someone who is not Tom.

Those differences are deep enough that this is a new type rather than an existing session with a microphone bolted on. Three properties define it: the conversation is held open by a connection rather than rebuilt per message; the thing Tom talks to and the thing that does the work are two different models in two different places; and strangers can operate it.

The names and files behind this section

The existing session host is the program tts-session-host, in the Jarvis repository under worker/session-host/. The five never-ending sessions are defined by one text file each in worker/session-host/persistent/, named dump, briefer, builder, observer and todo. The record keeps seven tables; the two that matter here are the one naming every session and the one holding each session's rows. The transcripts live in a directory shared by both Claude logins and are copied nightly into an object-locked storage bucket that no agent credential can delete from.

Why the box has to hold a connection of its own

This is the structural fact everything else follows from, and it comes from the supplier's documentation rather than from preference.

The speech model is OpenAI's GPT-Live, which takes speech in and emits speech out directly rather than chaining transcription, then a text model, then synthesis. It is full duplex: it can listen and speak at the same time, which is what makes interrupting it work. It is built to hand hard work to a second model, which the documentation calls delegation, and it offers exactly two arrangements. The choice is made when the conversation is created and cannot be changed afterwards; attempting to change it returns an error naming the field as immutable.

The first arrangement lets OpenAI run the second model. Its configuration names a model, gives it instructions, and gives it tools from OpenAI's own catalogue, such as web search. The second, which the documentation calls client delegation, means the speech model announces that it wants help and then waits for whoever is already connected to send an answer back over that same connection.

Two facts make the choice for us. First, the speech model has no tool list of its own at all: the only place tools can be declared is inside the delegation configuration, so there is no way to hand it a function directly. Second, there is no field anywhere in that configuration for a web address, hostname or callback that OpenAI could call. I had both checked against the full schema. This matters because the tools Tom wants the voice to have are on the box: reading the record, searching his files and his past sessions, reading the research cluster, starting a build. OpenAI cannot reach any of it, and the box has no public address to be reached at.

So the box must be the party holding a connection, and the documentation provides exactly the one needed. Besides the connection carrying audio, a conversation accepts a second attachment intended for a server that wants to observe and steer a conversation whose audio it is not carrying. On that attachment a server receives the running transcript of both speakers and may send text in, but may not send audio. That is precisely the shape wanted here.

The finished arrangement therefore has two attachments to one conversation. The phone holds the audio: the page asks a route on tom.quest to create the conversation, because the account credential must never sit in a web page, and OpenAI returns what the browser needs to open a direct audio connection. The box holds the second attachment and through it watches what is said and contributes text. A new program on the box does this, and it wants a plain name describing what it does rather than a coined one: the voice session host.

One alternative deserves recording because it is the only other way the box's tools could be reached, and it is not recommended. The schema does list a tool type for connecting an external tool server to the OpenAI-run backend. If that worked, OpenAI's own model could call the box directly. But the written guide names only two tool types as supported, plain functions and web search, and that external-server type is one of the thirteen the guide omits — so it is listed but undocumented. It would also require giving the box a public address, which it does not have and which is a larger change to Jarvis than this whole proposal. Mentioned so the decision is informed, not revisited.

The exact mechanisms, for an engineer

The speech model is gpt-live-1, the only identifier in its family, with a 128,000-token context window and a knowledge cutoff of 31 July 2025. Its page carries no label marking it preview or generally available, so treat its status as undeclared. A conversation is created by a server posting to the live sessions endpoint under the account key, with the browser's connection offer carried inside the JSON body; the reply carries the answer the browser needs. The browser's events travel on a data channel labelled oai-events, created before the offer. Because the browser holds no credential, the configuration offers a permission list restricting which events an untrusted front end may send and receive; omitting it allows everything, so set it explicitly. The box's attachment is a WebSocket to the same session identifier; it may not send audio and may not start the session, but may send the other nine client events, including all three text-append events. Creating a conversation bills fifteen seconds of voice time up front, credited back once it runs — but a conversation created and then abandoned still costs that. Rate limits are counted in concurrent sessions, fifty on the entry paid tier, and the free tier is listed as unsupported.

Context engineering: seven layers and one narrow pipe

This is the part that decides whether the thing is impressive or embarrassing, and it is unusually constrained in a way that turns out to be clarifying.

What the speech model knows arrives in seven layers. Four are set when the conversation is created and then frozen — the documentation states that the instructions given to the speaking model, the model itself, the voice and the startup history are all immutable after startup, and that changing the prompt means starting a new conversation. The other three arrive during the conversation through three events the box may send, each capped at five hundred tokens of plain text, roughly three hundred and fifty words.

The frozen layers are generous in size, which surprised me: the instructions accept up to 16,384 tokens, and a startup history of prior conversation may carry up to 128 messages and 8,192 tokens. So the constraint is not that the voice knows little. It is that everything it knows at the start is decided before the first word and cannot be revised, and that the only channel afterwards is narrow.

The first frozen layer is the persona: who it is and how it takes turns. Turn-taking deserves emphasis because it is the opposite of what an engineer expects. GPT-Live has no setting for interruption sensitivity — none. I had the full configuration searched: there is no threshold, no silence duration, no detection mode, and, stated explicitly in the documentation, no voice-activity detection or noise gate provided for this purpose at all. Turn-taking is controlled entirely by prose, and the documentation supplies a template with three headings to keep, covering how often it should make acknowledging noises, what it should do when interrupted, and when it should hand work to the backend. For a loud room it offers an extra block instructing the model to keep listening through pauses and not to treat a cough, music or a nearby conversation as a request. The behaviour one would expect to tune with numbers is tuned with sentences, and those sentences are part of the context.

The second frozen layer is the ground: what the voice may know about Tom. This is where the privacy problem lives. Jarvis holds private files describing who he is, what he wants and what he knows. None of it may be in the voice's context, because the voice is a loudspeaker in a room containing other people, any of whom can ask it anything. So the ground layer is not those files. It is a separately written, deliberately bounded description holding only what he would be content to have read aloud to a stranger. The third frozen layer applies the same discipline to live data — the date, where he is, what he is dressed as, and a few facts from the record chosen for being harmless. The fourth is the startup history, which is how a new conversation can begin knowing what a previous one covered, and it is text only: prior speech cannot be replayed as audio.

The three live layers are how everything the box learns gets in, and they differ in kind rather than degree. One carries text the model should say aloud, which the documentation warns is paraphrased in the model's own words rather than read out verbatim. One carries facts to know silently and use later if they become relevant, without announcing them on arrival. One carries instructions, and it is the only one that can cut the model off mid-sentence, which the documentation names as the way to stop a model that is saying something it should not.

Five hundred tokens per message is the defining constraint, and it is the right thing to design around rather than against. The box can never pour context into the conversation; it must decide, for every fact, whether that fact is worth three hundred and fifty words of the budget, and whether it should be spoken, known silently, or used to steer. The useful consequence is that the choosing happens on the box, by a model holding the full private context and all the tools, rather than inside the speaking model. The box thinks with everything; the voice is told the conclusion.

One more fact shapes long conversations and is worth knowing before it surprises him. There are no controls over what happens when the context window fills. The documentation says the model summarises older history in the background, and that once usage passes ninety per cent it starts a replacement engine inside the same conversation, handing it the original instructions and up to 8,192 tokens of recent history and summary. No event announces this. The original instructions survive; conversational detail may not. The design consequence is direct: anything that must not be forgotten lives on the box and is re-sent when relevant, never left to survive in the conversation.

That whole structure is also the privacy wall, and this is the part I would most want Tom to agree with. There is no reliable way to filter a model's speech after the fact, and no way to stop someone in a room from asking a question. The only wall that holds is that private content never enters the conversation at all. Since every route in goes through four frozen layers written once and three capped events sent by one program, that program is the wall: a single place, written as a program rather than as an instruction an agent is asked to follow, where what may be said aloud is decided. Nothing private reaching the voice becomes a property of the architecture rather than a hope about a model's discretion.

Three speeds of answer

A spoken conversation is unforgiving about delay in a way a typed one is not, so the design sorts questions by how long they take and keeps the fast path genuinely fast.

Most questions never leave the speaking model. It already holds the persona, the ground, the opening state and the history, so the date, what he is dressed as, who he is, and anything conversational come back immediately with no other part of the system involved. This is the path that makes it feel alive, and it is why the frozen layers are worth spending care on.

The second speed is a question the box can answer by reading. The speaking model delegates, the box receives the announcement, works out from the transcript what was actually asked, reads the record or searches his files, and sends the answer back as text to be spoken. This takes a second or two. One wrinkle the documentation is explicit about: the announcement that work has been delegated does not contain the question. It carries only an identifier and a timestamp, so the box must assemble the request from the running transcript itself, including short follow-ups such as a correction to something said earlier.

The third speed is real work — starting an ordinary Jarvis agent with the full tool set, which may take a minute or more. Here full duplex pays off, because the conversation does not stop. The box sends silent progress notes as the work proceeds and a spoken result when it lands, and the documentation's own guidance is to instruct the model to acknowledge the request and explicitly not to guess the result while waiting. For work much longer than that, the documentation suggests closing the conversation and starting a new one when the answer is ready, which also stops the per-second charge.

Four cautions, all of them things the documentation either states plainly or conspicuously does not say, and all worth knowing before building rather than after.

The transcript carries no turn boundaries at all. The documentation says fragments do not define complete turns and that no event marks the end of a spoken reply, so grouping speech into turns is the box's problem and will be approximate.

Whether audio already sent to the phone is discarded when Tom interrupts is not documented either way: the words for truncation and interruption do not appear in the GPT-Live documentation, there is no interruption event and no speech-started event, and the guidance points at the client managing its own playback. That reading is mine, not a quoted fact, and it is the first thing to measure with real hardware.

Nothing in the service helps with the acoustics. There is no noise reduction, no echo cancellation, no far-field handling, and the documentation explicitly refuses to provide a noise gate. Everything acoustic belongs to the browser and the hardware. Since full duplex means the model listens while its own voice is coming out of the same speaker, and the documentation does not discuss that interaction at all, the speakerphone's own hardware echo cancellation is carrying the entire design. That is a hardware requirement rather than a preference.

Finally, the supplier's own content filtering can cut the model off. The documentation describes two behaviours: some filter hits end the conversation outright, and others silence the rest of what it was saying and emit only a generic error. So an unexplained mid-sentence stop is a thing that will happen occasionally and should be handled rather than debugged.

What it may do, and the two walls

Jarvis is held together by four promises, two of which this design puts under new pressure. The first is that private things stay private. The second is that only Tom speaks for Tom: nothing reaches another person as him, ships publicly, or spends money without his approval or an automatic check passing.

The new pressure is that a voice session is operated by whoever is within earshot. Every existing agent is driven by Tom, by a program, or by a scheduled job. This one can be addressed by a stranger at a party, who can ask it for facts and ask it to do things. Nothing in the existing design anticipated that.

Two walls answer it, and both are places in a program rather than rules an agent is asked to obey. The first is the list of tools the box-side agent may use, which in this proposal is read-only: it may read the record, search his files, his past sessions and the research cluster, and read the web, and it may not write code, open a change, send a notification, message anybody, or spend anything. The second is the append filter from the previous section, the single point through which anything reaching the spoken conversation must pass.

Money is bounded separately and is simpler than it looks, with one trap. The conversation is billed by wall-clock time at five cents a minute, charged per second without rounding, and the documentation is explicit that active time includes every second in which nobody is talking and every second the backend is working. Muting the microphone does not stop the clock — which matters here, because the prop's on-off switch is a hardware mute button, and pressing it silences the microphone without ending the conversation or the charge. Three dollars an hour is the cost of leaving it open. The box-side work is billed like any other agent on the box. The platform supports a genuine hard spending limit that makes requests fail rather than merely warning, set per project, so this gets its own project, its own key and its own ceiling; the documented gaps are that the limit is monthly rather than daily and that enforcement is not instantaneous, so a little may spill past it. A closing rule on the box, ending a conversation that has gone quiet, is the practical control, and the documentation pushes that work onto the application precisely because no server-side idle timeout exists.

One deliberate omission, at Tom's instruction: the remaining access-control question — whether only his voice should be able to ask for certain things — is left for later rather than designed now, on the grounds that it should not shape the build. The two walls above are in the design because removing them later is easy and adding them later is not.

Where it lands in the record

The fourth promise Jarvis makes is that Tom can see what ran: every machine change and consequential action appears in the record within minutes, shown where he already reads. A voice session is the first agent whose conversation happens in the air, which makes it the easiest one to lose, so it gets the same treatment as every other session rather than a lesser one.

It gets a row in the record naming it, marked as the voice kind. It gets a transcript file in the same shared directory as every other session's transcript, assembled by the box from the fragments of both speakers — approximately, for the reason given above. That transcript is copied nightly into the object-locked bucket with everything else, so a conversation survives the box. Each delegation the box handles writes a row, so the record shows what was asked and what was done, and anything it starts is visible the way any other agent's work is. On tom.quest it appears in the same session list as the others and reads as a conversation.

Two limits worth stating. The transcript is what the supplier transcribed, which the documentation warns may contain mistakes, and for the model's own speech it is a transcript of what was generated rather than of what came out of the speaker. And a dropped connection cannot be rejoined: every recovery path produces a new conversation, either by continuing from a stored recording or by starting fresh with text history. Since a phone losing its signal is unlikely to close the old conversation cleanly, the practical plan is to keep the transcript on the box and start a new conversation from text — which is the fourth context layer, and the reason it exists.

Keeping the audio is possible but optional. Storage is off by default; switched on, the supplier retains the recording for thirty days and will return it as a two-channel audio file with his voice on one side and the model's on the other, and that stored recording is also what makes continuing an interrupted conversation possible. It is a real decision rather than a detail, because it means a recording of a party exists on someone else's servers, including the voices of people who did not agree to it. See decision six.

Decisions for Tom

Six, in the order they constrain each other. The first cannot be changed later without rebuilding; the rest can.

  1. Client delegation, so the box is the mind. The alternative is letting OpenAI run the second model, which is less work and brings web search immediately, but it cannot reach the record, his files, the cluster or a build, because no part of the configuration can name an address on the box and the speaking model has no tool list of its own. Taking the box-side route is what makes this a Jarvis agent rather than a clever toy, and it is why the two-connection design exists. The mode is fixed when a conversation is created. Recommended: client delegation.
  2. Read-only at first, with one proposed exception. The voice may read everything the box can read and write nothing. The exception worth considering is the writing that is already safe and already exists as single-purpose routes: logging one of his day facts — a meal, a weight, a training session, something he did — and adding a todo. Both are trivially correctable and would make the thing useful rather than only impressive. Anything that spends, sends, or changes code stays out. Recommended: read-only plus day facts and todos.
  3. Anyone in earshot may speak to it. The alternative is requiring a phrase or recognising his voice before it answers. Since the public-safe ground layer is what actually protects him, and a costume that ignores the person talking to it is a worse costume, recommended: anyone, with the context as the wall.
  4. A closing rule, because the clock runs through silence and through mute. Three dollars an hour accrues whether or not anyone speaks, and pressing the prop's mute button does not stop it. For everyday use the box should close a conversation that has gone quiet and open a new one on demand, carrying the text history across. For one evening in a costume, leaving it open is simpler and the whole night costs less than a cinema ticket. Recommended: a closing rule for ordinary use, suspended for the costume.
  5. It is a full session in the record, not a lesser thing. A row, a transcript, rows for what it did, and a place in the session list, exactly as a typed session has. The alternative is treating it as a transient toy that leaves no trace, which would make it the first agent in the system he could not look back at. Recommended: a full session.
  6. Do not store the audio. Storing it gives two things: a recording he could listen back to, and the ability to continue a conversation that dropped mid-sentence rather than restarting it from text. It costs a thirty-day recording of whatever room he was in, held on someone else's servers, containing people who did not agree to be recorded. The text transcript on the box already covers remembering what was said, and restarting from text is adequate. Recommended: storage off, which also means the continuation path is the text one.

What this leaves unchanged

Nothing about the five never-ending sessions changes: they keep their text files, their logins and their jobs. The existing session host is not modified and not involved, because a voice conversation has no per-message process for it to run; the new program sits beside it. No existing table in the record changes shape; a voice session uses the session table and the transcript directory exactly as a typed session does. The merge gate, the one path by which code reaches the main branch after its checks and audit pass, is untouched and still the only way anything lands — and the voice cannot land code, because in this proposal it cannot write at all. The nightly copy to the locked bucket needs no change to cover the new transcripts, since it already copies the directory they live in. The delegate, the agent that decides in Tom's stead when he is away, is not involved: a voice session exists only while he is talking to it, so he is present by definition. The other agents' models, prompts and costs are untouched. And nothing here changes the hardware decisions already settled for the prop, except to make one of them load-bearing: the speakerphone's own echo cancellation is now the only thing standing between full duplex and a model that interrupts itself, because the service provides no acoustic help of any kind.
